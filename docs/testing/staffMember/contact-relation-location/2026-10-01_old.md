## Investigation and changes

- Observed failure: relations were a static Angular `RELATIONS` array. The
  Contact form mixed `LookupStore` State data with a separate District signal,
  did not clear dependent selections consistently and had no Locality field.
  Employee creation did not add a Contact row.
- Confirmed cause: source references showed the hardcoded list feeding three
  forms/displays, while the shared LookupStore already owned the complete
  location hierarchy. `EmployeeContact` also lacked `LocalityId`, and its DB
  ContactNumber column was non-nullable.
- Changed behavior: backend enum/query/API is the only contact-relation catalogue;
  Angular consumers share it. Initial contact is added to the Employee aggregate
  before the repository SaveChanges within the existing transaction. Contact
  DTO/entity/repository/UI now carry LocalityId.
- An initial combined 40-test run reported two failures: the profile permission
  characterization did not yet list the newly approved token-only query, and
  `LocalityRefactorTests.Four_country_postal_seed_is_idempotent_and_populates_locality_postal_code`
  references absent repository file `database-scripts/SeedFourCountryPostalLocalities.sql`.
  The characterization was updated to recognize the narrow approved exception
  and passed in the final 30-test run. The missing historical seed fixture was
  not fabricated or marked passed; the nine applicable locality tests were rerun
  separately and passed.
- The executed tests establish enum ordering, authentication boundary, null
  placeholder values, additive migration source, route surface, Angular request
  shape, cascade calls and affected build compatibility. They do not establish
  actual PostgreSQL persistence, authenticated HTTP or deployed behavior.
