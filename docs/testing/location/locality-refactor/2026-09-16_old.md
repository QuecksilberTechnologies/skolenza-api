## Investigation and changes

The existing `SyncDistrictsFromCities.sql` intentionally copied City.Id to
District.Id, so the migration can establish the District FK deterministically.
The migration includes a compatibility City view so the currently deployed build
can continue reading during coordinated rollout.

## Persistence and cleanup

The target migration renamed the 8,333-row catalogue, populated every DistrictId
and LocalityTypeId, seeded LocalityType ids 1–3, backfilled TenantLocation where a
locality existed, and retained the temporary City compatibility view. These are
intentional permanent changes. No files are stored by these endpoints.

The follow-up migration removed District.PinCode, added required StateCode,
DistrictCode and LocalityCode values, and added nullable Locality.PostalCode. Direct
reconciliation returned zero missing State, District, or Locality codes.

The GeoNames postal seed is additive and idempotent. It reconciles legacy states
and districts by stable code or case-insensitive name, preserves existing primary
keys, and classifies postal rows as `Other / Unclassified` because the postal
source does not provide a reliable City/Town/Village field. GeoNames attribution
and CC BY 4.0 license details are retained in the generated SQL.

Direct reconciliation found 8,333 null PostalCode values, all belonging to the
preserved legacy catalogue whose source had no postal field. The newly imported
four-country postal rows have source postal codes; null values were not replaced
with fabricated data.
