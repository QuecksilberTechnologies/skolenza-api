# Student fee reversal calculation — 2026-11-01

## Scope and limitations

WIP. The central allocation helper can calculate a partial reversal against one
payment's previously allocated heads. It applies reversal to late fee first,
then reverses head priority and head-ID order, after subtracting amounts already
reversed. It rejects duplicates, imprecise currency and amounts above the
available reversal balance. This calculation is not connected to an endpoint,
database ledger, balance, receipt, gateway or actual money movement.

## Test and evidence

Synthetic input: tuition 1,500; another head 500 with 100 already reversed; late
fee 50. Reversal 300 returns 50 late fee and 250 from the second head. The test
also checks over-reversal, invalid currency precision and a previously reversed
amount larger than its original allocation.

Pre-change scratch Student **179/179**, protected **91/91** and **41/41**.
The first post-change Student run had **179 passed, 1 failed** because the new
test mistakenly expected 1,900.01 to exceed an available 1,950. After correcting
the test input to 1,950.01, Student **180/180**, protected **91/91** and **41/41**
passed without skips. Commands and guarded scratch connection are documented in
[fee allocation evidence](../fee-head-allocation/2026-11-01.md).

No database, Angular, gateway or deployed changes were made in this follow-up.
Offline reversal persistence and authorization, adjustment receipt and balances,
idempotency/concurrency, multi-installment batches, gateway refund and actual
provider acceptance remain pending. An accounting reversal is not proof of a
cash or gateway refund.
