## Implementation checkpoints

1. Establish a versioned key-history model and exact ownership/protection rules without changing the existing key or relaxing uniqueness on real data. Preserve a deterministic mapping for legacy records; fallback based solely on successful CBC decryption is unsafe.
2. Inventory all readers, writers, workers, token claims, key-derived lookup hashes and queued commands. Define and test a consistent cross-instance write fence, cutover, rollback and old-token behavior before switching any active key.
3. Build additive, reversible migration and synthetic fixture coverage on a dedicated disposable Local database. Verify encryption round trips, pending worker items, card uniqueness, concurrency, cache behavior, login and refresh coexistence, and rollback for failures.
4. Only after these checks and recoverable backup verification, separately plan environment-specific application and acceptance. The user's Local-only approval does not by itself establish Render acceptance.

These are implementation checkpoints, not a claim that the schema, key versioning or rotation endpoint exists. The full disposable-database test remains blocked by the previously rejected restore-and-cleanup operation; the user was asked to prepare a dedicated scratch database.
