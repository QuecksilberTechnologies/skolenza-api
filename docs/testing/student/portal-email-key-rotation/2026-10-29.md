## Investigation and changes

- The user authorized a Local-only safe shared-key design and tests, with existing Bank data and login preserved. No Render work is authorized by this decision.
- The inherited locked Bank and profile/contact pre-change commands select old `Employee` test names and execute **zero tests** in the current Skolenza project. These commands cannot be counted as passing. The registry now records the current `StaffMember`/`Institution` selectors while retaining the historical commands. Current Bank **1/1** and contact/profile **52/52** passed separately. No test assertion or locked product behavior was changed.
- Read-only source inspection confirms the active key is used by login and refresh handlers, SMTP configuration, Student official-ID encryption and portal/gateway protection. The resolver caches the key. CBC Bank ciphertext lacks a key-version marker; simply trying historical keys does not establish safe or authenticated Bank recovery. Numeric ID encoding currently uses the global salt in the inspected implementation; string decoding uses the institution key. These paths need separate compatibility tests before rotation is attempted.
- Other pre-change checks: locality **9/9**, institution creation/update **15/15**, role mapping **26/26**, and protected Staff/Curriculum plus Local rollback **41/41**, all with zero failures/skips.
- Additional consumers identified in source include encrypted device-command payloads, institution cards and their key-dependent lookup hashes. Existing JWT access tokens contain an institution-key claim, and the process memory cache can retain an old key for up to six hours. A safe operational design must account for active tokens, distributed processes, concurrent writes and rollback; replacing the DB key alone is unsafe. The solution must not print secrets or invalidate existing login contracts without separate authorization.
- Release solution build: **0 errors, 16 warnings**. No key lifecycle code, key material or database schema was changed during the selector reconciliation.
- Read-only Local schema inspection confirmed `UQ_InstitutionKey_InstitutionId UNIQUE ("InstitutionId")`; it is not conditional on active status. One institution cannot retain two key records in this table.
- The existing active-key resolver feeds more than Student email, including Bank encryption, encoded identifiers and authentication-related flows. A Student-only fallback cannot establish safe key rotation across those consumers.
- The experimental inactive-key lookup and related code were removed after the failure. No existing unique constraint, key, Bank data, production domain or Render record was altered.
- A reviewable direction is a versioned key history with at most one active key, retained previous key material, an atomic rotation procedure and explicit compatibility/migration tests for all existing consumers. Changing the shared reference needs specific user authorization under repository rules; existing locked Bank behavior must not be weakened.
