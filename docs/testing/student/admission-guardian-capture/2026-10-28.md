## Investigation and changes

- Observed gap: Guardian profiles and links could only attach to an already-created Student, while admission is saved before Student approval.
- Confirmed cause and evidence: `StudentGuardian` requires `StudentId`; admission had no Guardian association table or subresource routes.
- Changes: added `StudentAdmissionGuardian` entity, DTOs/handlers/repository methods, GET/POST/PUT/DELETE admission subresource routes, existing permission-pipeline mappings, filtered unique EF/SQL indexes for active links and one primary Guardian, and approval-time copying into `StudentGuardian`. Captured links may only change for Draft or Returned for Correction admissions; the existing Guardian profile is reused. SQL addition is in `database-scripts/CreateStudentAdmissionsAndRecords.sql`.
- Limits: contract tests and source review do not prove SQL application, runtime permissions, PostgreSQL transaction behavior, authenticated HTTP or deployed behavior. A Guardian is not required yet because no required-Guardian policy is approved. Final approval is not yet atomic with document review and fees.
