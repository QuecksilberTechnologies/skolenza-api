## Observed behavior

- The UI displays HTTP 400 message `The request is invalid.` while creating a Tenant.
- The Host create request DTO inherits `PermissionRequestDTO`; `ModuleId` and `OperationId` are required by the established Host permission pipeline.
- `HostRuntimePermissionValidator` returns the same generic validation message when either identifier is missing or zero, before Tenant field validation starts.

## Evidence and root cause

| Check | Expected | Actual | Result |
| --- | --- | --- | --- |
| Tenant create contract tests | Existing valid permission-context flows pass | 7 passed / 0 failed / 0 skipped | PASS |
| `HOST_TENANT_LIST` Add mapping | Active module-operation and Host-role grant | Module 28, Add operation 2, HostRole 1 | PASS |
| `HOST_TENANT_CREATE` operation mapping | At least one active create/Add mapping and Host-role grant | No row returned | FAIL |
| Validation error detail | Identify missing ModuleId/OperationId or unavailable create permission | Generic `The request is invalid.` | FAIL |

The dedicated create page can resolve `HOST_TENANT_CREATE`, but the canonical seed supplies no operation mapping for that module. Permission discovery can therefore produce no valid Add operation. A missing or zero permission identifier reaches `HostRuntimePermissionValidator`, which throws the generic validation error seen in the UI.

## Applied correction

1. The canonical seed now maps the canonical `Add` operation exclusively to
   `HOST_TENANT_CREATE`.
2. The obsolete `HOST_TENANT_LIST/Add` `ModuleOperationMapping` row is hard-deleted.
3. Host permissions are rebuilt from the corrected canonical mappings, so Host-Super-Admin receives
   `HOST_TENANT_CREATE/Add` through the existing permission pipeline.
4. Final seed verification fails if the create mapping is absent or the obsolete list mapping exists.

The generic missing-context response was not changed in this scope.
